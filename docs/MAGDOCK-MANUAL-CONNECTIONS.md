# MagDock 手动与同步启动的连接上下文

开发分支增量；安装/发布版本保持0.3.7，完整型号保持0/100。它关闭前一轮 [StreamLease](MAGDOCK-CONNECTION-LEASES.md) 中手动请求与启动绑定的缺口，不代表底座或鼠标完整验收。

## 实际行为

只读 View 返回当前打开 Session 的 connection_key。手动应用、重置、音乐开始/停止都必须带预览连接；动画启动另带 expectedDockConnection，不把它放入可导出、导入或保存在本地的 EffectConfig。后端在停止现有灯效之前先检查调用方连接，随后整个操作继续使用绑定访问；不会用新的只读发现替换旧请求的连接，也不会在操作完成后调用可能重新打开设备的无上下文 view。

当前正常请求在同一个 Session 内读取、持久化备份、再次核对原状态、设置并读回；回复仍带相同连接。应用或重置失败不会自动打开另一只底座。旧请求不会停止已有的新连接效果线程。电脑独立 RGB 不要求底座连接参数，底座独立编辑沿用 stop_for_dock 的输出归属规则。

界面把草稿归到读取到的连接；出现不同连接就换成该设备的数据，旧颜色草稿和错误提示不覆盖新数据。读取有请求顺序与操作 epoch，迟到的旧发现结果不能覆盖新读取。缺失连接会清掉旧底座控件并阻止底座同步；已勾选但不可用的底座仍能取消勾选，便于继续单独选择电脑 RGB。识别或取消勾选不启动灯效。

底座音乐状态、音量条和错误也按音乐线程的连接显示，新连接不会继承旧线程的运行状态或错误。

## 验证

新增5项默认原生测试覆盖所有手动/启动入口的过期、空和其他连接请求；同一请求不能先停止已有实际原生效果线程；正常 apply/reset 的读取、备份、命令和回复连接；新连接不继承旧音乐状态；真实音乐线程使用模拟电平发出12颗灯珠颜色并恢复。

测试注入的仅是峰值读取器，生产默认仍在音乐线程内打开 Windows 播放设备电平，不新增运行依赖。满电平、亮度3、基础颜色17/34/51时，源算法缩放0.66产生11/22/34，实际生产颜色流逐灯珠核对。此测试没有读取实际音频、访问麦克风或启动屏幕取色。

构建的 React 使用 Rust 导出的两个 View。10项界面检查产生8次请求：原生重放6次正常请求和2次过期请求，涵盖 apply/reset/music/stop、不同连接草稿、旧发现结果、启动竞争、导出不带连接以及缺失标记。回放直接走命令使用的 Controller 路由与 Engine，正常音乐使用模拟峰值、正常静态效果使用实际效果线程；过期请求无底座通信。原有19项电脑/底座独立 UI 检查继续通过，其后端仍为有状态 IPC 模拟，不当作实际PC RGB证明。

默认原生707项通过、55项默认忽略；新导出 fixture 和请求回放两项显式运行通过。TypeScript、Vite、非测试开发构建通过。没有新增依赖、图片、实体 HID 通信、原厂代码执行、固件/配对写入或安装操作。[验证记录](development/2026-10-27-magdock-manual-context-validation.json)。

## 剩余缺口

多底座明确选择仍未完成，多个匹配接口继续拒绝任意选择。连接 generation 不是硬件序列号。原厂63字节 WebHID data 与现有65字节 HIDAPI 写出（含ID）的物理描述符/末尾 padding 对照、真实音频/屏幕/LED效果、完整备份恢复用户入口和型号验收继续待做。这里的同步启动模拟不证明真实屏幕或PC RGB设备能够跟随。

后续已执行[0.3固件实体设置/音频通信及恢复核对](MAGDOCK-FIRMWARE03.md)，修复基础模式保留和输入队列问题；byte9含义及光学显示仍未解决。上文保留原增量的只读/模拟边界。
