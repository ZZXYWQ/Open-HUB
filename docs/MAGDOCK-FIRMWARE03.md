# MagDock 0.3 实物通信与音乐同步修正

开发分支增量，完整鼠标仍0/100，安装和发布版本保持0.3.7。实体底座设置测试与恢复已经执行；没有访问鼠标DPI/按键/宏、固件/DFU/配对或原厂恢复命令42。原厂Watcher/Agent后台保留运行，未结束这些进程。

## 实物发现与实现修正

固件本地显示0.3时，进入音乐同步的线上请求为 mode5 + sync1，但回读保留进入前的基础模式。原实现按写入mode5要求精确读回5，因此真实设备会使音乐和所有共用逐灯流的动画启动失败。已在每次mode5写入前读取当前设置；仅此已观察固件以原基础模式为预期，其他字段继续精确核对。其他未观察版本不继承例外；若前置读取与调用方已核对的状态不同，在SET前拒绝，不把外部新基础模式吸收到旧任务中。

StreamLease与音乐停止恢复改用写后实际观察状态，避免将线上5当作基础模式恢复条件。UI已有按sync显示音乐的处理，仍保留基础模式用于恢复。真实底座分别从基础模式0/1/2/3/4进入同步，均回读同一基础模式和sync1，并退出到原基础模式；这五个转换都有实际响应记录。

第二个问题是读取队列上限。所用hidapi2.6.7 windows-native在源代码中配置64个输入缓冲，原32次排空检查会在持续发送颜色帧后失败。现允许最多128个旧报告并包含额外空队列探测，仍有有限上限；32/64/65/128个旧报告及无限持续输入分别测试。实际音乐诊断也保证异常读取后仍停止/加入线程，保留可恢复前像，不能因线程提前退出但恢复成功就把音乐测试记为通过。

## 不能认定为独立睡眠字段的 byte9

第一次严格实物测试在原厂GET响应payload9变化时停止，随后用明确读取/预览的备份恢复了测试前完整30字节载荷。实验所用蓝分量160/0与该字节同步变化；原厂Afe虽然把它命名sleepSwitch，但全局灯效和固件信息两个直接消费者没有使用sleepSwitch/sleepTime。[静态AST事实](development/magdock-reader-consumer-facts.json)只覆盖这些直接调用，不证明全程序没有其他间接使用，更不证明固件中它没有睡眠作用。

严格自测保留原拒绝逻辑；另设明确的 `--magdock-characterize-light` 实验诊断，逐步记录payload9，不把它当作已证明独立状态。该诊断保护payload10..28及固件/已知Light字段，最终要求包含byte9在内完整30字节载荷恢复一致。因此不能把“受保护字段保留”误解为byte9含义已解决，或已证明任何颜色不会影响睡眠。

## 实际执行证据

最终完整实验包含六种原厂模式请求、五次基础模式进入音乐和五次退出、三组12颗RGB颜色帧、灯光关闭及最后恢复。17份设置响应实际读回，帧41仅证明传输完成，没有灯珠 framebuffer 回读或光学确认。测试后完整声明载荷与最初红色流水一致。[实际响应向量](../src-tauri/tests/fixtures/magdock-firmware03-physical-settings.json)去掉临时连接号与备份父目录，保留原始设备响应；只供测试，不进入运行资源。

真实Windows播放端电平链路又运行约三秒，最终发送58帧，期间线程运行且无错误，停止后已知设置与完整30字节载荷恢复一致。读到的电平约0.0000305，接近静音；这不是强音乐信号下的节拍、颜色或灯珠显示验收。

探索阶段有三类失败，均保留记录并明确读取当前状态后恢复：byte9不符合原固定字段假设、基础模式回读与mode5预期不同、旧32报告上限。没有把这些失败隐藏为通过，也没有在不确认当前连接时盲目重开另一只底座恢复。`--magdock-restore-backup <path>`沿用生产预览/摘要/当前状态检查供明确诊断恢复使用。
