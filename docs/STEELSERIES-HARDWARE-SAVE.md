# 赛睿明确板载保存

开发增量；未生成安装包、未安装，不增加完整型号验收数。仅 Rival 300 `1038:1710`、Rival 310 `1038:1720`、Sensei 310 `1038:1722`、Sensei Ten `1038:1832` 开放。

设备页面增加“保存已应用设置到鼠标”。先应用完整 DPI（旧三款固定两档，Sensei Ten 为 1–5 档与当前档）、回报率、全部已知非主左键及两个灯区，再单独请求保存；改动草稿、未应用的模板、连接改变、当前状态与成功应用记录不同，均不能直接保存。普通应用和配置导入不会自动写闪存。离线编辑器没有此按钮。

保存请求携带当前控制连接的随机新鲜标记，原生端在设备管理锁内核对精确型号、当前连接、完整计划和该设备最近一次成功应用的会话状态。标记不进入 Profile / 持久设备所有者。按字段内容比较草稿，JSON 序列化的字段次序及省略的可选默认值不会误判成新修改。连接重新打开后，旧请求零写入；新连接仍需重新读取并成功应用方案。

当前使用软件宏、尚有临时恢复记录或正在等待释放时禁止保存，防止 F13–F24 软件宏触发映射留在鼠标中。解除软件宏并停止、完成恢复后，还要重新应用完整硬件方案。保存另一只鼠标不会停止正在运行的鼠标宏，也不会向它发保存命令。

每次成功应用只允许一次明确的保存尝试。先落盘记录已知计划、型号和会话来源，再发送独立来源已核实的单条命令：Rival 300 Windows/HIDAPI `[00 09 00]`，Rival 310 / Sensei 310 / Sensei Ten `[00 59 00]`。短写或报错不重发、不自动回滚闪存；结果不明时也消耗此次尝试，用户须重新应用后再手动请求。审计记录不是闪存原始备份。

这些型号不能回读完整配置或闪存确认。成功界面只说明命令已发送，不声称持久化已回读验证。协议来源为 STEELSERIES-NATIVE-SOURCES.json 中固定的 rivalcfg 维护者逐型号 profile 与独立旧规格 `test_save`，未执行或分发参考软件。

原生测试通过实际生产驱动和内存传输检查三个精确保存报文、应用与保存的分离、不完整/无效/软件宏方案、旧连接、同路径重开、草稿/缓存改变、跨鼠标隔离、审计文件失败和不确定短写/错误。界面使用原生 DTO 检查按钮条件、字段顺序、连接请求、修改后重新应用、每次一次和软件宏拦截。实际 UI 请求另行验证：旧打开实例的连接标记必须被新原生实例拒绝；重新读取并应用后，只发对应型号保存命令。均为模拟，没有赛睿实物覆盖。
