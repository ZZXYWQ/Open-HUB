# GG 私有两灯区灯效导入

开发增量，仅 Rival 310 `1038:1720` / Sensei 310 `1038:1722` 的已核对平面字段布局；未发布或安装，不增加完整型号验收数。只读原始 GG SQLite 数据库；不运行厂商迁移 SQL、脚本或二进制。

GG122 已提取的界面模块提供了独立证据：两个精确型号共享配置装饰器 98871，使用 `logo_lighting` / `wheel_lighting` 的初始颜色、设置掩码、子类型、颜色/位置表及速度。Logo / 滚轮分别引用效果 0 / 1，坐标为原点。之前仅提示未转换的这些字段现在参与完整候选转换与原生预检。

常亮/关闭使用掩码 1、子类型 0 和初始 RGB；黑色关闭。颜色渐变使用掩码 0、子类型 1，保留 1–10 个已知模型颜色点和顺序。多色呼吸使用子类型 2、最多四个颜色，在相邻颜色中点插入黑色；原生控制点支持精确的半百分比位置，因此 16.5% 等黑色中点能够保留；四分之一百分比等其他未支持精度拒绝，不做静默取整。两张原始数组均严格核对 14 项布局。方向、主机串流、响应、覆盖色、其他未核实位和灯区引用不转换，整份候选被拦截，不能只保存其中 DPI 伪装为完整方案。

存储的 GG `speed` 不直接当原生毫秒。界面模块 48386 的周期计算是 `round(max(330 × 颜色数量 × 呼吸倍数, 10 × speed))`，呼吸倍数为 2、渐变为 1；已知速度滑块为 33–3000。导入按这个 UI 计算周期，再向原生编码器请求对应毫秒，默认 speed1000 得 10000 ms。此证据只证明 GG 界面节奏计算；本项目没有测量 GG 和这些实物的最终输出时序，不能宣称物理效果完全等价。独立 rivalcfg 原生向量用于检验字段打包，不用其原生 1000 ms 示例冒充 GG 存储单位。

UI 的转换说明及品牌条目包含灯效范围。导入后可查看两灯区、颜色、顺序、周期和原始宏，编辑、模拟再保存。操作不自动应用鼠标，也不触发板载保存。已激活效果会保存到 Open HUB；原厂未激活的调色历史不搬运。没有灯效记录的旧来源不补造颜色；只有一个灯区或悬空引用会拦截。

验证包括原厂迁移中的惰性默认 LED JSON、独立完整原生报告、错误掩码/位置/颜色/方向/布局/周期、实际 SQLite 候选解析，以及两型号四种模式的八组实际 UI 编辑保存。保存后的 Profile 经生产存储重载/合并和真实驱动内存传输回放，两灯区和原始五步混合宏保留；未支持的响应模式候选没有保存入口。来源文件 SHA-256、工厂编号和限制见 development/gg-lighting-static-schema-evidence.json。厂商 JS 只作静态解析，未加入软件包。

半百分比位置的编码、旧整数 JSON 兼容及拒绝规则详见 NATIVE-GRADIENT-PRECISION.md。
